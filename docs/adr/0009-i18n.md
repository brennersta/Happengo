# 0009. Internationalization

- Status: Accepted
- Date: 2026-11-16

## Context

The product is English and Brazilian Portuguese. The old UI mixed a dictionary with hardcoded English, and it formatted dates in the browser's zone with no zone stored on the event. Events in the inventory sit in Tallinn, Helsinki, and Santa Luzia. Those zones have to survive a viewer who is somewhere else. API error text translated on the server would split from the client catalogs.

## Decision

Supported locales: `en` and `pt-BR`.

The signed-in preference is stored on the user profile ([ADR 0003](0003-data-model.md)). With no preference, use the device locale when it is `en` or `pt-BR`, otherwise `en`.

The client uses i18next with ICU messages. Dates and times use the Intl API. Render an event's instants in its IANA `time_zone_id`. When the viewer's zone differs, show the viewer's zone as well. Intl uses the active locale, so month names and hour cycles follow `en` or `pt-BR`.

The API returns ProblemDetails whose `type` is a stable code. The client translates that code. The server does not localize free text. Title and description stay in the language the author wrote.

"Happening now" is the UTC comparison in [ADR 0003](0003-data-model.md). The display zone does not move the instant.

## Consequences

- A new language is a client catalog and a profile value. The API grows no string tables.
- `type` codes are part of the contract. Renaming one breaks the client copy.
- Authors and viewers can disagree on language without the database storing a second title.

## Open

On-demand translation of title and description. The old app offered it. No provider is chosen here, and the API does not translate event text until one is.
